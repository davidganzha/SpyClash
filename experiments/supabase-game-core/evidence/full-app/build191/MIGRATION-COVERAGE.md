# Build 191 migration coverage and identity review

Reviewed source baseline: `a32c8e9c`, 2026-10-19. This is a source-based design review, not evidence that an import or deployment ran. No production writes were performed for this review.

Production execution and subsequent readback are recorded separately in [PRODUCTION-MIGRATION.md](PRODUCTION-MIGRATION.md). This document retains the original design review and its scope limits.

## Completion contract

The tracked source schemas name **27 entity types**, including the built-in `User` principal. Independent remote schema inventory and two complete row scans confirm **26 deployed types, 1,148 original rows, and no unknown remote types**. `AccountDeletionReceipt` is confirmed absent rather than an empty deployed table. Preserve every deployed entity's original rows, identifiers, timestamps and content in a private immutable archive, with explicit counts, canonical digests, pagination completion, and read errors. A complete product migration additionally requires that user-visible data can be read through the actual target handlers. An archive by itself does not restore an inbox, grant, friendship, history list or profile.

The current candidate still delegates **sign-in verification, AI generation/quota, production billing verification, APNs delivery and original-account deletion** to Base44. Copying their records does not remove these provider dependencies. Preserve that distinction in completion claims. The data import must not change secrets, provider settings, webhooks, subscriptions, send notifications, generate login sessions, or replay delivery jobs.

## Entity-by-entity disposition

`Materialize` means prepare a target representation consumed by current runtime code. `Delegate + archive` means preserve the exact source records while the existing provider remains authoritative; do not activate an unverified copied credential or entitlement. `Archive` means durable preservation without restarting obsolete transient work.

Counts and digests are recorded separately in `source-summary.json` and `remote-schema-inventory.json`; raw values remain in the restricted `.local/bulk-migration` archive and are excluded from this report.

The 22 rooms comprise 11 waiting and 11 finished rooms; none is playing. These room records are preserved as history, not restarted as target sessions. The only invite is expired and references an absent room. An actionable waiting-room invite or playing room would block the current ancillary plan pending an explicit handoff implementation. This is a documented limitation of live-room continuation, not loss of the source room records.

Both announcements are withdrawn; preserving those states produces no new broadcast. All notification events have terminal delivery states (`no_devices`, `cancelled` or `failed`). Visibility additionally depends on committed inbox projection and the current friendship/room: existing friendship projections refer to accepted friendships, so none is actionable in the source inbox. The plan imports five bound historical friend events with `visible=false`, archives the other 332 transport records, and never calls notification delivery APIs. The source inbox does not expose its `game_started`/`game_finished` transport records as personal inbox items.

Nine read receipts have current source owners and are materialized with remapped item keys; two absent-owner receipts remain archived. Existing target watermarks can only increase. The single open moderation report is materialized with both reviewed account mappings. Missing/deleted report principals would remain null in active columns with their original immutable identifiers retained privately; they never create an account.

The actual ancillary dry plan has **2 announcements, 5 hidden events, 9 read receipts, 1 report, 0 visible notifications, 0 issues and 0 warnings**. It records all 374 ancillary source rows, including 357 archive-only dispositions. The 13 focused tests cover event/receipt ID linkage, source visibility, target request supersession, unresolvable visible items, read watermarks, withdrawn announcements, provenance replays, target edit/deletion preservation, collisions, report tombstones, live-room handoff rejection, a target-state recheck before writes and full PostgreSQL timestamp precision in baseline reads. ## Identity and first-login safety

The proposed bulk contract from `bulk_core` is appropriate if these invariants are enforced by both planning and application:

1. Resolve existing `legacy_links` and `legacy_session_accounts` by immutable legacy user ID and canonical source origin/app ID. Existing owner UUID always wins. A conflicting link/reservation, non-active profile, deletion intent, or deleted billing/account subject is a blocker, never an instruction to recreate the identity.
2. For an absent identity, persist a unique `legacy_session_accounts` reservation before Auth creation. Use the same SHA-256 identity-key formula as `legacy-session/service.ts`: `origin + '\n' + appID + '\n' + legacyID`. Assign a random, private shadow mailbox; do not use source email or a publicly derivable mailbox. Validate that the reserved UUID is not already another Auth/profile principal.
3. Use the server-side Auth Admin API for exactly the reserved UUID with `legacy_provider=base44` and the immutable identity key in **app metadata**. Never accept user-editable metadata as ownership evidence. Verify the returned/recovered UUID, mailbox, provider marker and identity key, including after lost acknowledgement.
4. Auth rows are needed before history/pack/member writes because those target tables reference `auth.users(id)`. Profiles/reservations themselves intentionally do not establish authenticated ownership. Reservation rows have no Auth FK so they survive Auth deletion as immutable ownership evidence.
5. Bulk import must not manufacture `legacy_links.verified_at`, `last_verified_at`, Auth sessions, passwords, login links, or email sends. Preserve `state=reserved` for never-authenticated imports. `import_completed=true` can describe data completeness only and requires compatibility with the first-login importer.
6. First login must still call the fixed canonical Base44 `User/me` endpoint with that user's current credential, bind the returned legacy ID to the reservation, validate Auth metadata, and only then create the verified link and issue the session. Matching email, SPY-ID, display name or a copied export row is never proof of login ownership.
7. Recheck target account/link/deletion state and reservation identity inside the final transaction, using the existing account-then-legacy lock order. A plan digest is not concurrency protection. A user can log in, edit a profile, delete an account or create a friendship between plan and apply.
8. Rollback must not delete an Auth account that has since logged in, gained sessions/verified ownership or new user data. Preserve reservations/tombstones needed to prevent later reassignment. Record partial Auth-creation outcomes separately from the transaction; database rollback does not undo Auth Admin calls.

Auth data belongs in private schemas or correctly protected tables. Supabase documents referencing the Auth **primary key** and protecting application profile data with RLS; Auth Admin creation is a server-side privileged operation. [User management](https://supabase.com/docs/guides/auth/managing-user-data), [Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser).

## Progress and history reconciliation

`profile.ts::projectedProfiles` calculates rating, played/won totals and per-role statistics from `full_game_private.history` using `competitive-stats.ts`. The Base44 `User` schema describes its counters as legacy server mirrors. Therefore copying User counters into profile JSON alone will not restore visible progress.

The safe default is to import complete canonical history and keep source counters as independently checked evidence. Do **not** sum source counters with newly imported history, and do **not** take a maximum between source/target counters: both can double-count already imported matches or convert stale mirror errors into ranked credit.

Produce a per-user reconciliation of: source raw mirror counters; source deduplicated ranked history totals; source owner-visible history count by local/online, ranked/unranked and spy count; pre-existing target history/stats; newly inserted canonical matches; final projected target history/stats. Imported matches already present through the login importer must not be inserted again under a new namespace. Native Supabase matches must remain intact. An unexplained loss of visible progress is an unresolved migration result, not a successful import with an archival footnote.

`deduplicateCompetitiveHistory` retains non-ranked rows; `isRankedOnlineHistory` controls scoring separately. Stable `player_user_id` takes precedence over email even if that ID is deleted or absent. Email fallback is acceptable only for a genuinely ID-less historical row and a unique verified source-owner association, and must stay `ranked=false`. It must never bind authentication or bypass an explicitly different stable owner.

## Loss and collision cases to account for

- Missing/duplicate source users, duplicate SPY-IDs, SPY-ID disagreement with an already migrated active profile, or a reserved manual SPY-ID belonging to another account: stop for an explicit conflict decision. Never silently allocate a replacement SPY-ID.
- Dangling friendships/comments/history/pack/report references to deleted or unavailable users: retain original rows and report exact disposition; do not fabricate active users or attach them to a same-email account.
- Multiple source friendship records for one unordered pair: target allows one. Reuse canonical pair policy and preserve blocks; a newer target removal/block must not be overwritten by an old accepted source row. Each non-materialized original must remain in archive with reason.
- Already imported rows from legacy login use deterministic `spyclash-legacy-import-v1` mapping; existing social import uses a different social namespace. Reuse existing provenance/target IDs. Mapping every row with a new bulk namespace causes duplicate packs/history/comments or conflicting pairs.
- Distinct retained history rows can collapse onto target `(match_id, player_id)` after ID mapping. Count and explain such collisions instead of treating `ON CONFLICT DO NOTHING` as successful preservation. Reusable room codes are not match identities.
- Pending friendship events require consistent `friendship.request_event_id` and `notification_events.id`. Copying only a pending friendship restores Requests but not the personal Inbox. Read receipt prefixes must reference the same remapped IDs.
- Current inbox retention is 90 days with an epoch of `2026-07-27`; expired/withdrawn/old notifications may be intentionally absent from runtime while still archived. This is different from dropping still-visible notifications.
- Target announcements require metadata absent from some old records; target reports constrain reason/status; comments cap body length; packs constrain words and counts. Invalid legacy data must be quarantined with loss accounting, not truncated silently.
- Source `created_at` and built-in `created_date` may differ. Preserve originals and use a documented precedence consistently for runtime ordering, deduplication and inbox read comparisons.
- Export pagination by offset can miss or duplicate records while Base44 changes. A final per-entity re-read/digest check or frozen source snapshot is needed before claiming a coherent complete export; two different captures must not overwrite immutable provenance silently.
- Archive files include private messages, contact details, moderation reports and encrypted credentials. Keep raw export and preimage backups outside Git, with restricted filesystem permissions; commit only sanitized counts/digests/reports. Never log row bodies or secret environment values on errors.

## Required verification before claiming completion

- All 26 deployed entity exports complete and the one absent tracked schema is explicitly recorded; every source row has an archive hash and a materialized/delegated/archived/quarantined disposition. Aggregate row counts alone are insufficient.
- All intended users appear in the target directory with unchanged SPY-IDs and correctly preserved existing accounts; no authenticated sessions were created by import.
- First verified login adopts a pre-reserved user and preserves imported profile/history/social state; wrong legacy credentials, wrong metadata, duplicate contact emails and deleted accounts cannot claim it.
- Re-running the same snapshot creates no additional users, history, packs, comments, memberships, events or Auth sessions. Changed snapshots cannot overwrite target data without conflict review.
- Friendship accept/cancel/block flows work across an already migrated and a newly reserved account. Imported pending inbox notifications and prior read state match the intended source visibility.
- Progress/history reconciliation has no unexplained decreases or duplicate ranked credit. All original private content remains recoverable in the archive.
- Provider-backed membership, AI quota and account deletion remain correctly routed and clearly described as delegated until a separate provider cutover is verified.
- Rollback is tested against both an untouched import and one where a user has since logged in/edited data; it must refuse unsafe rollback rather than destroy subsequent user work.
