## Additional gaps found in the deployed runtime

Comparing the real production baseline with the branch found two relevant corrections already present in source but not deployed. They are included as narrow additions to the prepared candidate rather than silently copying the entire branch function:

- Legacy roster exit could fail with `400 membership_generation_invalid`: the server emitted an email-based legacy token which its own expected-membership validator rejected. The expected-token validation now accepts the server's bounded legacy format without relaxing generation IDs for new memberships.
- Profile-signal fanout released profile ownership before obtaining only the recipient lease. Concurrent profile deletion could therefore finish cleanup before a late signal was created. The candidate holds both identities, rechecks ownership at each write and finishes started sibling work before release. Injected tests cover deletion before admission, deletion while writing, lost ownership before create/update and healthy multiple recipients. This is a confirmed code-level race; no claim is made that it caused the reported 409 screenshot.

The touched push function also receives bounded scalar error logging, including its retry/backfill paths. This avoids passing arbitrary/cyclic SDK objects to logging; the production logger itself was not observed crashing. Other pre-existing branch differences remain outside this repair. The exact files, tests and production baseline are in [the staged scope](backend-staging.md).

The broader candidate test run then exposed a reachable terminal-completion race: a guest leaving a finished room could win the room revision comparison between the completion read and write. The side effect had already succeeded, but the old helper reported failure and left its marker processing until its recovery timeout. The connected correction rereads and retries the exact completion token without redispatching the side effect or overwriting the guest's change.

The same review distinguished this correctness bug from intentionally retained sequential behavior. Committed-start signal fanout is now moved after participant lease release together with its required update-only/no-create policy. Profile repair adopts the connected parallel-mirror barrier and serialized fanout implementation; all started work is awaited before ownership release. Those are deliberate reductions in lock duration and contention, not evidence that sequential execution itself corrupted results. The final candidate must pass its full applicable function suite; earlier partial passes are not sufficient.

## AI operation contract and tradeoffs

The new entity is server-owned and admin-only. It stores a request fingerprint, ownership token, state and confirmed result; it does not store the raw theme or credentials. Account deletion removes its rows through the existing protected cleanup path.

The protection applies to calls with a stable `request_id`; the current iOS client supplies it. Legacy requests without that field retain compatibility and do not acquire a durable journal identity. The journal is separate from the old expiring response cache: running and completed markers are retained until account deletion. Storage therefore grows with generation requests. Deleting old markers based on age would re-enable an old ambiguous request and requires a separately reviewed request-retention protocol.

An ambiguous transport failure stops automatic provider retries/fallback for the same execution. Intentional semantic quality/expansion calls inside the generation algorithm remain possible. The journal does not assert that each logical generation always uses a single external API call. If quota was reserved before a crash, this change does not infer that the provider did no work and silently refund or retry it.

When durable preparation is unavailable, new idempotent work fails before quota or provider effects. A confirmed journal result can replay without the legacy store; a confirmed legacy result can replay during a journal outage. A missing confirmation is never counted as a successful commit. Localized client messages distinguish temporary recovery unavailability from an unknown prior outcome.

The Arsenal editor previously kept reusing its pending request ID after every error. For the new confirmed `generation_outcome_unknown` response, that would make every explicit retry hit the same permanent refusal. It now invalidates only that exact current request after the typed response; the next user tap allocates a new ID. Ordinary network failures and journal outages retain their ID for safe replay. Old account/signature/request callbacks cannot invalidate a replacement attempt, and the error handler never starts a generation itself. Local and online game setup already allocate a new ID on each explicit generation action.
