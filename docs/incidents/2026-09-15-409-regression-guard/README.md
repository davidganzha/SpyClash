# Build 158: защита от повторного появления 409

## Результат

Пакет подготовлен поверх `70118515` / Build 157, ветка `davidganzha/409-regression-guard`.
Маркетинговая версия остаётся 1.0.2; номер сборки синхронно повышен до 158.

Выявлен конкретный риск регрессии: исходная папка `/Users/davidganzha/Documents/SpyClash`
оставалась на `f3469363` / Build 148, тогда как актуальный сервер уже содержит большой
фикс Build 157 из задачи «Устранить все ошибки 409». Публикация целых функций из старой
папки могла бы затереть новые исправления. Это подтверждённое расхождение источников,
а не доказательство, что именно такая публикация вызвала каждый пользовательский сбой.

Повторная read-only выгрузка 15 сентября подтвердила **17 функций / 197 runtime-файлов**:
все хеши и конфигурации совпадают с `2026-09-15-409-hardening/deployment-postflight.json`.
В этом пакете нет изменений серверного runtime, схем или секретов. Исправления Build 157
для шести функций сохранены в истории исходной ветки; заново публиковать их из старой папки нельзя.

## Дополнения

- iOS упорядочивает игровые команды одного экземпляра клиента, включая выход и закрытие комнаты.
  Чтение комнаты продолжает работать независимо, поэтому обновление состояния не ждёт записи.
- Отменённая или просроченная команда удаляется из очереди до отправки. Время ожидания
  вычитается из бюджета запросов с заданным тайм-аутом. Таймер ожидания отменяется при выдаче очереди.
- Ответы и ошибки старой сессии отбрасываются, в том числе при выходе и повторном входе
  с тем же токеном. Существующие правила безопасных повторов Build 157 сохранены.
- `check-release-baseline.py` отклоняет checkout без опубликованных исправлений в истории.
  С `--remote-dir` проверяет все серверные файлы и конфигурации против проверенной базы;
  потеря, добавление или изменение файла останавливает проверку. На старой папке проверка
  фактически вернула `STALE_CHECKOUT`; на новой ветке и свежей выгрузке — PASS.
- GitHub Actions запускает серверные тесты и тесты сетевого клиента iOS при изменениях
  исходников, конфигурации и скриптов. Workflow не публикует приложение и не меняет сервер.
  Настройки обязательных проверок защищённых веток этим пакетом не менялись.

## Следующие изменения и выпуск

Продолжать работу из этой ветки/папки или её потомка, содержащего Build 157.
Перед передачей изменений выполнить:

```sh
sh scripts/check-409-resilience.sh
sh scripts/check-409-client.sh
```

Перед подготовкой любого серверного пакета выгрузить **все** функции в новую временную
папку, затем выполнить:

```sh
python3 scripts/check-release-baseline.py --remote-dir /absolute/path/to/fresh-pull
```

Одна проверка ancestry без `--remote-dir` не проверяет текущий сервер. Даже успешная
проверка базы не сертифицирует произвольный candidate: пакет нужно собирать как проверенный
delta поверх свежей выгрузки и сверять итоговые хеши. Локальный checkout и production могут
иметь намеренные различия, зафиксированные в отчёте Build 157. Если сервер изменился,
сначала сверить новое изменение и обновить проверенную базу; не обходить ошибку проверки.

## Границы проверки

Очередь одного клиента уменьшает конкуренцию собственных команд; она не сериализует
разные телефоны. Серверные блокировки и допустимые 409 сохраняются. Принудительное снятие
чужой действующей блокировки не добавлено. Проверка двух авторизованных клиентов, реальный
сценарий после обновления и установка/распространение iOS Build 158 остаются отдельными шагами.
Этот пакет подготовлен локально; новая публикация и App Store/TestFlight не выполнялись.
