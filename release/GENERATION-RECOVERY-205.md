Status: **deployed on 2026-11-01 after explicit approval**; see
`GENERATION-RECOVERY-205-ACTIVATION.md` for read-back and production evidence.
This is a server-only change. The installed App Store client remains build 200. Build metadata is

## Problem and behavior

A provider call could finish but lose its completion acknowledgement. A later
database error was also incorrectly classified as a quality rejection whenever
any provider result existed. Both paths could strand a paid generation. In the
installed app, an unresolved 503 keeps a durable command; changed inputs then
produce a local `app_action_recovery_required` 409 before HTTP.

The new relay retries only authenticated outcome writes, at most three attempts
with fresh signatures and timeouts. Claims and provider invocations are never
automatically repeated after an ambiguous outcome. Provider/validation failures
report a signed, claim-bound terminal result. The private provider-call table
adds `failed` and a constrained failure code; quota stays charged when provider
execution may have occurred. No raw request inputs or exception text are added
to the failure records or logs.

A database interruption after completed provider work now releases only its
owned worker lease and preserves the result for replay. Only proven content
validation rejection becomes a terminal quality error. Terminal attempts return
422 so the installed app acknowledges its durable command. Unknown outcomes use
`generation_attempt_closed`, avoiding the older client's incompatible localized
override. The same terminal UUID never starts another provider call.

## Client limitation

A server cannot clear a 409 already produced locally by changed inputs. The user
must retry the original saved inputs to receive the terminal response, then
close/reopen the generator or change the inputs. Repeatedly tapping Generate in
the same editor with unchanged inputs retains its terminal in-memory UUID.
The Ukrainian generic 422 localization may hide the detailed server instruction.
A client recovery change is still required to eliminate this local lock in all
cases. This package does not claim that arbitrary provider outages cannot recur.

## Rollback boundary

The package includes exact original source for reference. Before enabling the
new Base44 relay, app-services can revert to that snapshot if necessary. After
any new `failed` provider row exists, **do not restore old app-services**: its
settlement logic does not understand that state. Revert Base44 first and retain
the compatible new app-services handler; review any further rollback separately.
Keep the additive migration and durable outcomes. Never erase claims to force
another paid call.
